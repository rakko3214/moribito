# Moribito 複数セッション作業分割

Status: Ready for use
Last updated: 2026-09-16

## 初回リリース範囲の更新（2026-09-21）

初回はユーザー決定により第1～3章をWeb/PWAで先行リリースし、ストア版は後続とする。Session A/Eの後半章制作は後続版へ回し、B/C/D/F/G/Hの第1～3章に必要な作業を優先する。本編は全12章。各担当は現在の変更状況を確認してから作業を開始する。

## 目的

本リリース残タスクを複数のCodexセッションへ分け、同時作業による上書き、仕様の食い違い、巨大なマージ競合を防ぐ。全体の残タスクは [`PRODUCTIZATION_BACKLOG.md`](PRODUCTIZATION_BACKLOG.md) を正とし、本書は担当範囲と統合手順を定める。

## 開始前の必須作業

2026-09-16時点の`main`作業ツリーには、追跡済み・未追跡を合わせて約210件の変更がある。この状態を複数セッションから直接編集してはいけない。

1. 現在の変更を内容別に確認し、動作する基準コミットへまとめる。
2. 全テスト、lint、型検査、本番ビルドを成功させ、基準コミットIDを記録する。
3. 各セッションは同じ基準コミットから、別worktree・別ブランチで開始する。
4. 元の作業フォルダは統合担当だけが使用する。

基準コミットを作るまでは、別セッションではコードを変更せず、読み取りと設計確認だけを行う。

## 共通ルール

- ブランチ名は`codex/release-<担当名>`とする。
- 1セッションにつき1ブランチ・1worktreeを使用し、同じフォルダを共有しない。
- 担当外のファイルを変更しない。必要な場合は統合担当へ「統合依頼」として内容を渡す。
- `package-lock.json`、セーブスキーマ、共通イベント型の変更は統合担当の承認後に行う。
- 無関係な変更をステージ、整形、削除、巻き戻ししない。
- 各機能は実装だけで完了にせず、単体テスト、統合テスト、実画面確認を行う。
- 仕様を推測で増やさない。未決定事項は`OPEN_QUESTIONS.md`へ記録する。
- 各セッションの完了時に、変更ファイル、テスト結果、未解決事項、統合時の注意を報告する。

## 作業の波

依存関係を守るため、全セッションを同時には開始しない。

```text
Wave 0  基準コミット・仕様決定
   ↓
Wave 1  A 物語仕様 / B マップ / D 戦闘 / G 本番基盤
   ↓
Wave 2  C UI統合 / E 後半章・妖怪 / F 正式素材
   ↓
Wave 3  H 全体QA・性能 / 統合担当によるRelease Candidate
```

## 推奨する開始順

1. Session 0で現在の210件の変更を確認し、基準コミットを作る。
2. Session A、B、D、Gを別worktreeで並行開始する。
3. Session Aの仕様承認後、Session Eを開始する。
4. Session B・Dの独立実装が固まった後、Session Cが画面へ統合する。
5. 仕様と画面寸法が固まった範囲からSession Fが正式素材を置換する。
6. R1～R3を統合後、Session Hが変更凍結した候補版を検証する。
7. Session 0が修正を再統合し、Release Candidateを判定する。

## 統合順序

競合と手戻りを抑えるため、原則として次の順で統合する。

1. A：承認済み仕様
2. B：マップ・当たり判定の独立変更
3. D：戦闘純粋ロジック
4. G：バックエンド・インフラ
5. E：章進行・妖怪・セーブ
6. F：正式素材
7. C：共有画面への最終接続
8. H：QA・性能・リリース設定

各統合後に最低限、次を実行する。

```powershell
npm run lint
npm run typecheck
npm run test:run
npm run build
npm run cdk:synth
```

マップ、UI、入力を含む変更は、自動テストに加えてローカルブラウザとスマートフォン実機相当画面で確認する。

## 禁止事項

- 複数セッションから同じworktreeを同時操作する
- 基準コミットが異なるまま統合を始める
- 他セッションの未コミット変更を含めてコミットする
- 共有ファイルの所有者へ連絡せず直接編集する
- テスト失敗を既知として放置したまま次の統合へ進む
- First Playableの完成を、本リリース完成として扱う
